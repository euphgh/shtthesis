## 2. 参数单位：统计位数，不是声明或实例个数

根据本轮读取的远端`transform/src/emu_integrate_system.cc`：

```cpp
uint64_t ff_count = 0;
for (auto &ff : database.get_scan_ffs())
    ff_count += ff.width;
scan_ctrl->setParam("\\FF_COUNT", Const(ff_count, 64));

uint64_t mem_count = 0;
for (auto &mem : database.get_scan_rams())
    mem_count += mem.width * mem.depth;
scan_ctrl->setParam("\\MEM_COUNT", Const(mem_count, 64));
```

因此采用以下口径：

| 参数 | 定义 | 本文单位与名称 |
| --- | --- | --- |
| `FF_COUNT` | 扫描寄存器条目的width之和 | bit，寄存器扫描状态位数 |
| `MEM_COUNT` | 扫描存储器条目的width×depth之和 | bit，存储器/SRAM扫描状态位数 |

`FF_COUNT`不是多位reg声明的数量，`MEM_COUNT`不是SRAM实例数、字数或BRAM/URAM块数。参数名为`MEM_COUNT`，不是`MEM_COUN`。所有十六进制值均按无符号数转为十进制；当前值均可精确表示。

若之后需要“扫描寄存器条目数、SRAM实例/条目数”，应另外统计对应扫描元数据条目，不能将这两个参数直接当作对象个数。本批仅收集上述参数的位数。

### 5.2 仅由本批参数支持的观察

- 同一DUT在2、3、4分区下的MEM_COUNT总位数均相同，但分布到各Part的方式不同。
- FF_COUNT总位数并非在所有DUT的不同分区数下都相同；PicoRV32保持1635 bit，其他DUT存在差异。这里只记录差异，尚未核对其来自哪些变换或扫描条目，不将其解释为状态丢失或额外开销。
- `rocket_part4/part3/EMU_SYSTEM_3.v`中的FF_COUNT和MEM_COUNT均为0。这说明该Part的这两类扫描状态计数为0，不等于整个Part不存在组合逻辑、接口或其他功能。
- 多个配置的存储器扫描状态主要集中在Part 0，具体以逐Part表为准；扫描状态位数分布不能直接代替物理资源利用率。

## 6. 与报告及其他实验的关系

- **1.3分布式状态提取**：提供各Part扫描寄存器/存储器状态规模，供解释局部Scan Dump与全局状态汇聚。
- **1.6状态管理开销**：作为扫描数据规模的来源之一，与实测保存/恢复耗时关联时，须匹配具体DUT、Part配置和RTL/bitstream。
- **2.1物理资源失衡**：这不是LUT、FF、BRAM、URAM、DSP综合占用，不能用它替代分项资源报告。

远端`EmuScanCtrl.v`按FF与MEM分别向上取整到64 bit字处理：

`scan_words = ceil(FF_COUNT/64) + ceil(MEM_COUNT/64)`。

因此，即便仅估算扫描传输字节，也不能不加说明地直接将两类位数相加后除8；实际分配还可能有页对齐。完整检查点还涉及内存模型数据、输入记录及元数据，需单独采集。本轮没有测量扫描传输时间、实际文件大小、保存/恢复耗时或扫描条目数量。

当前可直接填入实验材料的字段是**每Part的寄存器扫描位数、存储器扫描位数及其合计**。原始参数摘录与既有划分快照分别保存；生成目录名称相同不自动证明它们来自完全相同的一次构建。
