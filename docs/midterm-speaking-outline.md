# 中期答辩演说提纲

本提纲按Contents和正文第1—11页组织，对应`pptx/midterm/`中的独立页面。页码指正文内容编号，不包含封面与目录。每页列出讲述顺序、需要口头补充的内容和转场，不要求逐句背诵。

讲述主线：**大规模RTL需要多FPGA运行，但调试还需要一致的全局状态；REMUS围绕周期精确执行、一致暂停和恢复重放建立系统，再通过划分与运行控制支撑部署，最后说明原型结果及后续工作。**

背景第1—5页尽量简洁；第6页的一致暂停、第7页的恢复重放、第8页的实际资源分配是技术重点。第10页集中给出实验结果。标为“追问时展开”的内容不必在正式讲述中主动展开。

## 开场与Contents

**开场要点**

- 介绍课题“多FPGA硬件仿真关键技术研究与实现”，说明本次汇报关注中期完成的工作、实验结果和后续计划。
- 用一句话点出目标：让较大规模的RTL设计能够在多个FPGA上执行，并通过一致暂停、状态保存和重放支持调试。

**目录页讲述顺序**

1. 首先介绍研究背景，以及为什么多FPGA系统还需要可重放的调试能力。
2. 然后介绍四部分进展：执行与暂停、状态与重放、自动划分、可扩展运行控制。
3. 接着展示双FPGA原型及工作负载、性能实验。
4. 最后说明当前限制和下一阶段的工作安排。

**转场：**先从RTL设计的执行与调试需求说起。

## 第1页：从RTL仿真到多FPGA原型

对应标题：From RTL Simulation to Multi-FPGA Prototyping

**本页要讲清：设计规模和软件负载的增长，使单纯依赖软件RTL仿真或单FPGA都面临限制。**

**讲述顺序**

- 设计复杂度以及软件负载增加，验证的时间成本增加，常用的验证手段也发生变化
- 传统RTL仿真：内部信号容易观察，调试灵活，但运行长软件负载时耗时较大。
- 单FPGA原型：利用FPGA并行执行，提高运行速度，适合执行更长的软件流程，但单块FPGA的资源容量有限。
- 多FPGA原型：通过划分设计扩展容量，使较大规模SoC能够部署和运行。

**转场：**把设计放到多个FPGA上运行后，如何调试成为另一个问题。

## 第2页：多FPGA系统的调试需求

对应标题：Multi-FPGA Prototyping Is Fast, but Hard to Debug

**本页要讲清：能运行大型设计，还不足以支持对内部错误的定位和复现。**

**讲述顺序**

1. 多FPGA适合大设计和长负载；重点转向内部状态不易完整观察、出错过程不易复现。
2. 因此我们希望引入一个可重放的多FPGA仿真加速方案：先运行到关注位置，再一致暂停，保存全局状态，随后从检查点恢复并重放，生成需要分析的波形。

**转场：**要实现这个调试过程，需要解决以下四个相互关联的问题。

## 第3页：关键技术问题

对应标题：Key Challenges of Replayable Multi-FPGA Emulation

**本页要讲清：执行正确、暂停一致、状态可用和划分合理缺一不可。**

**讲述顺序**

1. **周期精确执行：**原本片内的组合逻辑依赖变成跨FPGA通信，必须保证数据传播完成后再更新DUT状态。
2. **全局一致暂停：**各分区进度可能不同，不能简单地分别停止后就提取状态。
3. **分布式状态管理：**需要把局部状态组织成全局检查点，并映射回恢复与重放所需的状态。
4. **自动化划分：**既要考虑资源分配和跨片数据量，也要考虑逻辑依赖跨分区的次数，即路径切割数。
5. 这些各自的问题学术界虽然在一些方向有过一些进展，例如Cycle-Accurate Exec与Automated Partition，但是在多FPGA仿真加速领域还是有空缺

**转场：**这些问题也说明了本课题与已有工作的衔接关系。

## 第4页：研究基础与目标

对应标题：Research Gap and Goal



**讲述顺序**
而在系统工作的方向上，相关工作主要分为两类：
1. 多FPGA原型系统提供容量与执行能力，但在调试上的支持仍有不足。
2. 课题组已有REMU提供单FPGA扫描状态提取与重放的基础，但单FPGA容量存在限制。
3. REMUS将这些能力扩展到多FPGA，重点解决跨分区执行、一致暂停、全局状态组织和重放之间的配合。

**转场：**接下来来介绍本工作的具体流程

## 第5页：REMUS总体流程

对应标题：REMUS: Overall Workflow and Mid-Term Scope

**本页要讲清：前面提出的能力如何组成从RTL输入到运行调试的完整流程。**

**讲述顺序**

- 顺着流程从RTL输入讲起：自动划分得到多个分区，每个分区的大小能放在一个FPGA中
- 然后将其部署到一个多FPGA系统中，系统中有数据路由系统以及主机控制的运行时
- 系统通过跨片通信执行DUT，由运行控制协调暂停
- 在一致的逻辑周期提取各分区状态，形成检查点，供FPGA恢复或软件RTL重放使用

**转场：**首先要保证分布在不同FPGA上的电路能够正确执行，并停在同一个逻辑周期。

## 第6页：周期精确执行与全局一致暂停

对应标题：Cycle-Accurate Execution and Global Pause

**本页要讲清：利用LI-TDM保证执行语义，再通过稳定采样和共同目标周期完成一致暂停。**

**讲述顺序**

- 采用DUOHUAFEN的LI-TDM技术作为基础，他结合了延时不敏感电路（LI）与分时复用（TDM）的优点，可以在延时不确定的信道中实现精确执行。
- 本工作对电路的状态机进行了优化，为逻辑周期中减少了一次数据交换，提升了执行效率
- 第二个工作，即使执行是周期精确的，暂停请求到达各节点的时刻不同，各分区仍可能处在不同周期。
- 我基于LI-TDM设计了一个软硬件结合的全局暂停方案
1. **先稳定进度。**请求各分区进入接收屏障，等待全部确认后，再读取各分区计数，避免采样时进度继续变化。
2. **再设置共同目标。**图中A位于42周期、B位于41周期，选择43为共同目标，分别配置A再走1步、B再走2步。
3. **最后推进并检查。**解除屏障，使各分区按配置推进；确认最终均已停止且到达目标周期，完成所需传播后，才进入状态提取。

**转场：**有了一致暂停边界，接下来才能把各分区的状态组织成可用于恢复的检查点。

## 第7页：分布式状态提取、恢复与重放

对应标题：Distributed State Capture, Restore and Replay

**本页要讲清：检查点既支持硬件继续执行，也支持回到软件RTL环境观察内部过程。**

**讲述顺序**

1. **Global Snapshot：**在同一DUT逻辑周期，复用REMU的Scan Dump机制提取各分区状态，并按状态映射关系组织全局检查点。
2. **FPGA Restore：**将检查点中的相应状态写回各分区，恢复寄存器、片内存储及相关内存内容，为继续执行提供起点。
3. **软件RTL Replay：**将分区状态映射回软件RTL模型，从检查点继续仿真，并按记录重放输入，生成内部波形。
4. 指向右侧实例：PicoRV32双Part Cosim保存非零周期检查点，软件RTL从该检查点重放；在后续同一逻辑周期，图中选定信号与参考检查点解码值一致。

**口头补充**

- 两条恢复路径的用途不同：FPGA恢复用于继续硬件执行，软件重放用于详细观察内部信号。
- 确定性重放依赖完整的相关状态以及相同的输入和环境行为，不能仅靠恢复几个寄存器。
- 这张对照图来自Cosim与软件RTL重放，支持所选信号在指定周期的一致性，不称为物理板卡的全状态、全区间等价证明。

**追问时展开**

- 起点检查点位于2048周期，比较位置为绝对周期42080，对应重放后的40032周期；两个Part中的六个选定信号目视一致。
- 本例2048周期后没有新的输入变化记录，重放保持输入值；变化外部输入的场景需要进一步验证。

**转场：**以上介绍了运行后的状态管理，下面回到部署之前，说明设计如何自动划分到多个FPGA。

## 第8页：自动化电路划分与实际资源分配

对应标题：Automated Multi-FPGA Circuit Partitioning

**本页要讲清：自适应粒度提高了建图与求解效率，但划分质量还要回到实际综合资源来评价。**

**讲述顺序**

1. 方法简述：根据RTL层次与规模选择划分粒度，构建超图，使用KaHyPar求解，再分析路径切割数，支撑LI-TDM传播阶段配置。
2. 初步观察用一句话概括：在层次较好的设计中，图规模和求解时间明显减小；目前Cut Size、权重均衡和路径切割数与网表级划分接近，最终结果仍在整理。
3. 把主要时间留给图表：KMH两个Part的LUT利用率接近，约73.2%和75.8%；FF约17.7%和8.2%，BRAM约14.3%和0%，实际资源分布并不均衡。
4. 得出当前问题：单一权重或某一类资源接近，并不能说明多种FPGA资源都得到均衡分配，需要引入更准确的多资源约束。

**口头补充**

- 图中是EMU_SYSTEM综合后的资源占用，百分比以整片器件容量为分母，不是划分器内部的节点权重。
- KaHyPar是采用的已有超图划分工具；本工作集中在粒度选择、建模、自动化衔接及路径分析。
- 当前图用于指出实际资源分配问题；尚不能单凭这组结果断言某一种建模因素导致不均衡，或证明某种算法全面优于另一种算法。

**追问时展开**

- 图规模约为原来的1/10、求解时间约为1/7是尚待最终确认的观察值，确认前不作为答辩中的正式定量结论。
- 后续需要在对应配置下联合比较划分指标、综合资源和实际运行性能。

**转场：**划分得到多个Part之后，还需要让主机能够方便地控制各节点、读写状态，并支持进一步扩展节点数。

## 第9页：可扩展多FPGA运行控制

对应标题：Scalable Multi-FPGA Runtime

**本页要讲清：将主机对各节点的访问统一起来，减少扩展时对主机PCIe连接数量的依赖。**

**讲述顺序**

1. 从左侧直连方式讲起：Host通过独立PCIe连接访问每个FPGA，实现直接，但节点增加时会受到插槽和PCIe资源限制。
2. 右侧Fabric方式通过Ref节点提供统一主机入口，其余节点经板间互连访问。
3. 主机以“目标节点＋局部地址”访问寄存器和内存，上层的一致暂停、状态操作仍使用统一接口。
4. 说明阶段进展：已实现相关访问组件与Driver后端，并建立双节点联合仿真环境；完整联合验收和板级验证仍需补充。

**口头补充**

- Ref也承载本地DUT与资源，不只是独立的转发设备。
- Fabric解决主机资源访问的扩展问题，不能直接等同于DUT执行速度提升；统一入口仍有共享带宽限制。
- 页面没有标注实现状态，但口头需要交代上述验证范围。图中的三个节点不代表已完成三板实验。

**转场：**下面展示已经搭建的双FPGA原型。当前这套板级实验采用的是左侧PCIe直连方式。

## 第10页：双FPGA原型与实验结果

对应标题：Dual-FPGA Prototype and Evaluation

**本页要讲清：系统已有真实板级运行结果，并取得了运行速率与一致暂停开销的初步测量。**

**讲述顺序**

1. 对照照片介绍平台：两块NM37/VU37P板卡连接同一Host，各自通过PCIe访问，FPGA之间使用QSFP/Aurora链路通信。
2. 按表介绍工作负载范围：PicoRV32、Rocket对应裸机程序，Nanhu、KMH对应OpenSBI/Linux类负载。重点展示材料较完整的KMH结果。
3. 指向终端截图：KMH已进入Linux交互命令行，说明系统能够承载较长的软件执行流程。
4. 给出性能数字：所测运行片段中，PicoRV32约0.327MHz，KMH约0.322MHz；Host侧一致暂停流程约0.8—1.1ms。

**口头补充**

- 这里的频率是DUT逻辑周期数除以实际经过时间，区别于FPGA物理时钟频率。
- 暂停时间包含Host发起协调、寄存器访问以及最终状态检查，不是单个硬件屏障的响应时间。
- 工作负载表概括评估对象，当前展示的Linux CLI证据属于KMH，不借用该图证明其他DUT的全部运行状态。

**追问时展开**

- PicoRV32频率来自两个较长运行片段；KMH来自一个检查点前运行片段，不是Linux整个启动过程或进入CLI后的平均频率。
- 暂停统计包含23条PicoRV32记录和1条KMH记录，属于现有日志的描述性结果。
- 若问检查点开销：KMH已有记录中，保存约80.1秒，主要时间位于memory阶段；不能仅据此认定瓶颈就是某一种硬件链路。相关分项保留在实验记录中，正式讲述不额外展开一组新指标。

**转场：**现有原型验证了系统的阶段能力，也为下一阶段的平台扩展和性能优化提供了依据。

## 第11页：后续工作

对应标题：Future Work

**本页要讲清：下一阶段围绕平台扩展、性能分析和划分质量形成可验证的结果。**

**讲述顺序**

1. **Fabric部署与四FPGA集成。**完成Fabric板级验证，建立四FPGA实验平台，验证更多节点上的运行控制和系统协作。
2. **性能分析与运行时优化。**在扩展平台上分析执行和通信开销，研究中断驱动控制以减少轮询，再依据测量结果确定优化重点。
3. **划分优化与评价。**承接第8页资源分布问题，改进多资源平衡与通信代价建模，同时观察实际硬件仿真性能，而不只比较图划分指标。
4. **论文整理。**汇总方法、实验配置、对照结果和验证边界，完成学位论文。

**口头补充**

- 四FPGA首先用于扩展部署容量和验证规模，不预设节点数增加就能获得线性加速。
- 性能分析与划分优化可以相互迭代；最终需要用实验判断改进是否有效。

**收尾：**目前已经围绕多FPGA执行、一致暂停、分布式状态管理及自动化部署完成阶段实现，并取得双FPGA运行和软件重放的初步结果。后续重点是扩大验证规模，完善性能与资源分配评价。感谢各位老师，欢迎批评指正。
